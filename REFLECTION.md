# Task 3: Reflection on the AI paradoxes

The most interesting paradox in this homework is that the ability that makes an agent useful also makes it vulnerable. A verifier needs to understand a CV written in ordinary language. It has to recognise that BSc and Bachelor of Science mean the same thing, connect a shortened name to a legal name, and decide which of several profiles belongs to the applicant. However, the same language understanding lets an applicant place instructions inside the material being checked. The agent has to understand the document without giving the document authority over the verification process.

My attack uses this tension directly. The CV upgrades Kelly Tsang's bachelor's degree to a master's degree. It also includes an invisible instruction that describes the false qualification as a formatting issue and supplies a supposedly canonical record. The intended mistake is not a failure to retrieve the correct profile. A verifier could retrieve the correct BSc and still approve the CV if it accepts the document's explanation of why the MSc should be ignored. This makes the distinction between evidence and instructions more important than the amount of information the agent can access.

A second paradox is that more information does not necessarily mean more certainty. A name search can return many plausible people. Adding a location filter helps, but the location in the CV could itself be false. A verifier that trusts the filter too much may never find the right person. Removing all filters creates a different problem: the result limit can hide the relevant profile. I therefore see identity resolution as a separate inference problem. Several independent attributes should identify the person before individual claims are judged. Finding a person with the same name is not enough, but requiring every claim to match would make it impossible to identify a person whose CV contains a lie.

A third tension is between automation and accountability. A reliability score looks precise, even when it reflects incomplete coverage or a failed request. A score of 0.95 is useful only if the agent actually checked the relevant facts. In my implementation, a passing result requires a retrieved primary profile, resolved identity and coverage of all five claim categories. An incomplete check returns 0.5. Under the homework's threshold this counts as a negative prediction, but in a real recruitment process it should trigger further review rather than an automatic rejection. An API timeout is not evidence that an applicant lied.

Finally, improving the defender and improving the attacker can happen together. Building a verifier reveals the assumptions an attacker can exploit; writing an attack reveals checks the verifier needs. This is productive when the exercise is controlled, as it is here with mock profiles. It also shows why one successful demonstration is weak evidence of reliability. A defended prompt may reject an obvious instruction but still miss a small date change, and a successful attack on one design may fail on another. I would judge the system through repeated tests, explicit discrepancy checks and separate reporting of service failures. The practical goal is not to make the agent sound certain. It is to make every decision traceable to the claims it checked and the evidence it retrieved.
